# CyberBrick MCP — 设计与踩坑笔记

> 合并自原 `HANDOFF.md`（交接/逆向结论）与 `PROBE_RESULTS.md`（动态验证记录），只保留仍然有效的内容；原文见 git 历史。
> 验证环境：macOS arm64 · CyberBrick v0.6.2（Electron 33.2.1 / Chrome 130）· 真机 RC_MODULE 接收器。
> 工具契约见 [`MCP接口文档.md`](MCP接口文档.md)；MPY/系统升级链路见 [`MPY固件链路笔记.md`](MPY固件链路笔记.md)。

## 1. 架构选型

**路线：CDP 驱动运行中的 App**。

1. 以 `--remote-debugging-port=9223` 启动 App（避开常用的 9222）。
2. MCP 用 `chrome-remote-interface` 连 CDP，对主窗口 `Runtime.evaluate`。
3. 调 App 自己的 `window.app.*` / `window.electron.ipcRenderer`——**加密、证书、配对、云端签名全部复用 App**，MCP 不碰原生协议。

| 被否决的方案 | 原因 |
|---|---|
| 独立重写串口/蓝牙协议 | B0 封包 + 加密在定制 Electron 的原生模块里（见下），需逆约 157MB 的 Electron Framework，固件升级易失效 |
| 只做不加密的部分（串口刷 MicroPython） | 可作补充，但收益有限 |

**前提——Electron Fuses**：`RunAsNode` / `NodeOptions` / `NodeCliInspect` 开启，`EmbeddedAsarIntegrityValidation` / `OnlyLoadAppFromAsar` 关闭；main.js 无 debug-port 过滤。App 升级后用 `npx @electron/fuses read --app <app>` 复查。

**加密在原生模块里**：`process._linkedBinding("electron_common_cuckoo")`（符号 `encodeB0Packet`、`parseB0Data`、`cuckooGrape/Lemon` 等，位于 `Electron Framework.framework`）。renderer 侧经 `ipcRenderer.encrypt` / `b0Encode` 调用即可，**不要逆它**。

**技术栈**：Electron + Vite + React 18 + TanStack Router + zustand + MUI/Radix；`esptool-js`、`electron-store`、`electron-updater`；无 `.node` 插件、无 wasm。设备通信走 renderer 的 **Web Serial / Web Bluetooth**，没有本地 HTTP/WebSocket 服务。

**逆向产物**（不在本仓库）：App 的本地副本 `CyberBrick.app`，以及解包后的 asar（`app.asar` 解出：`.vite/build/main.js` 主进程、`preload.js`、`.vite/renderer/main_window/assets/index-*.js` 前端主 bundle）。

## 2. App 运行时入口（`src/connection.js` 的 `KNOWN_PATHS`）

- `window.electron.ipcRenderer`：preload 桥，**main world 直接可达**（`contextIsolation:true` 但 API 挂在 main world），无需 contextId。70+ 方法均为 `[native code]` 黑盒，但 main.js 的 `ipcMain.handle` 实现可读。
- `window.env`：`{platform, arch, isPackaged, isPrimary, windowId}`。
- `window.app`（AppManager 单例）——**几乎所有工具都走这里，不手拼 B0 包**：
  - `bluetoothDeviceManager`（真实连接池 `bluetoothDevicePool`，**以 MAC 为键**；不是 `connectionPoolManager`）
  - `local`：`sendGetMessage`、`isInLoader`、`runSendConfigTask`、`sendTestCommand`、`getADCStatus`、`updateLoaderFirmwareMpy`、`requestDeviceById`、`triggerReconnection`、`disconnectAndForgetDevice` 等
  - `ipc`：含 `autoSelectSerialPort`
  - stores：`deviceListStore`、`useFirmwareConfigStore`（编辑器）、`useFirmwareListStore`（项目列表）、`progressStore`、`windowStateStore`（含 `closeSubWindow`）、`connectionLoading`

**字段映射（真机修正）**：设备对象用 `deviceName` / `deviceConnectStatus` / `deviceId`（MAC）/ `bluetoothDeviceId`（base64，推荐作为 device_id），不是 `name` / `status`；`local.isInLoader` 收 `{bluetoothDeviceId}` 对象而非字符串。

## 3. 设备协议要点

**命令枚举**：
```
BIND_DEVICE=0  UNBIND_DEVICE=1  BIND_RECEIVER_LIST=2  DEVICE_STATUS=3
GET_DEVICE_CONFIG=4  SET_DEVICE_CONFIG=5  EXECUTE_COMMAND=6  SET_PIN_CODE=7
SET_DEVICE_NAME=8  RAPID_RECOGNITION=9  GET_DEVICE_WIFI_MAC=10  GET_BOARD_INFO=11
SET_PRIVATE_KEY=12  REQUEST_CERTIFICATE_FILE_INFO=13  REQUEST_CERTIFICATE_FILE_BLOCK=14
COMMUNICATION_ENCRYPTION_READY=15  GET_BOARD_TYPE=16  DISCONNECT_DEVICE=17  KEEP_ALIVE=18
MPY_DEV_MODE=19  START_MPY_UPDATE=20  MPY_PROJECT_INFO=21  MPY_CHECKSUM_INFO=22
SYSTEM_VERSION=259  SYSTEM_UPGRADE=262  SYSTEM_REBOOT=263
```

- **明文豁免（`CE`）**：`[13,14,15,9,11,17,18,259,263,262,19]` 无需加密连接；其余命令 `sendGetMessage` 会先自动 `createEncryptConnection()`——MCP 无需处理加密。
- **GET / SET 路由**（App 内部真实分类，复用、别自己分）：GET `[2,3,4,10,11,16,13,14,259,263,262,21,22,19,20]` → `sendGetMessage`；SET `[0,1,5,6,7,8,9,17,18]` → `sendSetMessage`。
- **`GET_DEVICE_CONFIG` 是板载配置文件读写**，不是"设备配置"：`{reqType:0}` = 文件信息 `{file_size, file_chunk_size, md5}`（`file_size=0` 表示无板载配置），`{reqType:1, index}` = 数据块；空 payload 设备不应答 → 超时。
- **`SET_DEVICE_CONFIG` 写入**：FILE_INFO(md5,size) → FILE_BLOCK(index,is_tail,data)，chunk 150；真机 22 块写入、回读 size 与 MD5 一致。
- 结果码：`SUCCESS/FAILED/OLD_DEVICE/NOT_SET/RESET/FORMAT_ERROR`；PIN 相关 `PIN_MATCH/PIN_NOT_MATCH/PIN_NOT_SET/PIN_ALREADY_SET/...`。

## 4. 免弹窗连接

- **串口**：`ipc.autoSelectSerialPort({strategy:'first'|'new'})`——主进程 `serial-port-auto-select` 代转 chooser 回调。`file://` origin 对 serial/bluetooth 一律许可，不会被权限拦。`navigator.serial.getPorts()` 可非交互枚举已授权端口（不暴露 vendorId/productId）。
- **蓝牙**：`bluetoothDeviceManager.requestDevice()` + 监听 `bluetooth-devices-found` 广播 + `ipcRenderer.selectBluetoothDevice(deviceId)` 免 UI 选中（厂商过滤 17882 / 前缀 [99]）→ MAC 解析 → 入池 → B0 探测 → `addDevice`。

## 5. 项目管理的实现方式

App 的项目管理模块（`pa`）与打开编辑器辅助（`X1`）是 bundle **模块内部变量，运行时不可达**，但每一步都能用 App 自己的原语等价透传：

- create = `addFirmware(模板配置, name)`；模板数据提取自 bundle（`src/core/templates/*.json`，与 UI 创建的项目逐字节一致）。
- import = 同样的 `config_version` 校验 + `design_id`/`region` 改写 + `addFirmware`；store 的 zod schema 要求 10 个 sender channels 和完整 receiver 槽位表，极简 JSON 需补齐默认骨架。
- open editor = `setFirmwareConfig(getFirmwareById(id))` + `ipcRenderer.createWindowWithPath`（新窗口）或 `history.pushState` hash 路由（当前窗口；App monkey-patch 了 pushState 通知路由器）。
- 模板按 App 当前语言取 en/cn 变体（`localStorage` 的 `lang`，缺省按 `navigator.language`）；`none` 模板空配置会被 `addFirmware` 拒绝，不提供。
- `firmware_config_load_template` 用同一份模板数据 `setFirmwareConfig`（App 里并不存在 `loadTemplateById`/`loadDefaultConfig`）。
- `firmware_edit_actions` 的语义化文档（`src/core/action_docs.js`）已与 store 逐个核对。

## 6. 踩坑清单

**启动（`cb_launch`）**
- **单实例锁**：App 已在跑时，带 debug flag 再启动会静默退出；`second-instance` 只转发 deep-link 不转发 CLI flag → 必须先杀旧实例。
- **沙箱**：受限 shell 里启动报 `sandbox initialization failed: Operation not permitted`，~1s 内退出（复现 100%）→ 必须在非沙箱 shell 启动。
- **autoUpdater**：启动即检查一次（`autoDownload=true`、`autoInstallOnAppQuit=false`），不会静默安装，但 App 可能在两次会话间被用户升级 → `cb_health` 读 `navigator.userAgent` 报告实际版本。

**运行时**
- **BLE 掉线**：板子休眠/池清理会掉线，重跑 `connect_bluetooth`（或 `scripts/reconnect.mjs`）；重连后广播名可能变（`RC_MODULE` ↔ `CyberBrick-[xxxx]`）。
- **陈旧 GATT 链接**：OS 层残留连接导致板子不广播、App 扫不到 → 板子断电重启。
- **多窗口**：开项目编辑器子窗口后 `/json/list` 有多个 page，必须连 `window.env.isPrimary === true` 的主窗口（子窗口会把设备调用转发失败）。
- **renderer 卡住**：用户在编辑器操作时 evaluate 可能不回 → ping/evaluate 硬超时 10s，长流程 60s。
- **MD5**：renderer 的 `crypto.subtle` 不支持 MD5，在 Node 侧算好传入。
- **`runSendConfigTask` 要求 sender**：其 finalMode 硬编码 `send_config_and_pairing`，单接收器场景会被拒 → `flash_config` 默认改走底层 `SET_DEVICE_CONFIG` 文件协议。
- **不要自动 `addFirmware`**：旧实现在没传 `firmwareListId` 时把编辑器配置存成新项目再烧，导致项目列表出现「遥控小车 2」之类的重复项 → 高层路径改为要求已存在的 `firmwareListId`（缺省用编辑器当前 config id）。
- **注入安全**：所有拼进 `Runtime.evaluate` 的字符串用 `JSON.stringify` 转义。

## 7. 安全红线

- 登录 token 在 renderer `localStorage`（`cyberbrick_auth_token` / `cyberbrick_refresh_token`）；`sanitize()` 按 key 名过滤，**不读取、不导出**。
- 不用 `getBBLHeader`（云端签名头）、`getAesKey`、`get/setPrivateKey`、`validateCert`。
- 故意不暴露：`BIND_DEVICE`、`UNBIND_DEVICE`、`SET_PIN_CODE`、`SET_DEVICE_NAME`、`SET_PRIVATE_KEY`、证书流程（见 `src/core/devices.js` 的 `ALLOWED_COMMANDS`）。
- 设备绑定、PIN、私钥、固件升级类操作需用户明确确认（项目 `CLAUDE.md`）。server 其余部分是纯透传，但会升级固件的调用（`flash_mpy`、`flash_firmware`、带 `hardwareMappings` 的 `flash_config`）必须传 `confirm: true`，由 Agent 先向用户转述影响并获得同意；设备类写操作的目标必须唯一匹配一台设备（同名板子很常见，如都叫 RC_MODULE）。绑定、PIN、私钥、证书流程不暴露。
